# doc-writing — 小さく始めるドキュメント作成フロー

人に読ませる文書を「いきなり本文」で書くと、骨格のズレが本文を書き終えてから見つかり、書いた分が捨てになる。
このスキルは **目的 → H1 → H2 → 段落** の順で段階ごとに評価と承認を挟み、捨てる量を最小にする。

## 対象

- 対象: ユーザー以外の人が読む文書。Design Doc・ナレッジページ・FAQ 回答・マニュアル・提案文書・共有する調査計画や分析レポート
- 対象外: 日報・作業ログ・個人メモ・ADR（`/kb adr`）・調査ノート（`/kb research`）
- 叩き台も段階ゲートを1段ずつ踏む。ゲートを踏まずに書いて見せてよいのは、ブレインストーミングのメモと、調べたことを説明するレポートだけ
- このスキルは **工程と評価の時点** だけを持つ。文体ルールは [prose-rubric.md](./references/prose-rubric.md)、媒体ごとの書式（house style）は媒体側のファイルを参照する

## 工程の全体（各段階の入力・成果物・評価・ゲート）

| 段階 | 入力 | 成果物（ファイル） | この段階で評価すること | ゲート |
|---|---|---|---|---|
| 0 目的 | 依頼・参照資料 | outline ファイル冒頭の「目的」節 | 読者と読後の行動が 1 文で言えるか。文書の型が 1 つか。字数の予算があるか | ユーザーの一言 OK |
| 0.5 ファクトシート | 参照資料 | `facts-YYYYMMDD.md` | 数字ごとの条件と出所。数字を含むレポートのときだけ | なし（1 の材料） |
| 1 H1 | 0 の目的 | 同ファイルの H1 箇条書き + rubric 表 + 用語表 | 目的との整合・行動につながるか・分量（節数）・用語 | ユーザー承認 |
| 2 H2 | 承認済み H1 | H2 を足した箇条書き + rubric 表更新 | 制約・前提の出所、重複、具体例。2 モデルの外部レビュー | ユーザー承認 |
| 3 段落 | 承認済み H2 | `draft-YYYYMMDD.md` | TL;DR と本文の対応、文体ルール、house style | ユーザーが読む（承認は 4 の後でよい） |
| 4 外部レビュー | draft | draft 更新 | 2 モデルで、矛盾・次の行動が不明な箇所・誤り・用語 | ユーザーが反映後の draft を見る |
| 5 公開 | draft | 確定版ファイル / 公開ページ | 文体ルール・リンク切れ | ユーザーの最終承認 |

ゲートは段階 0・1・2・4・5 の 5 箇所。0・1・2 と、4 の後（公開してよいか）は「H2 はこれで承認ですか」のように明示的に聞き、
承認の言葉を待つ。個別の論点への回答は承認ではない。論点への回答がそろったら、次の段階に進む前にこの問いを出す。3 は見せるだけ。
rubric 表を書いたあと、レビューを反映したあと、に別途承認は求めない。
ユーザーが答えていない問い・決定事項を、答えが出たものとして扱わない。未回答のものは次の返信の冒頭に再掲する。
チャットでユーザーに求める判断は 1 メッセージ 3 件までにする。詳細はファイルに置き、チャットには判断とファイルの場所だけを出す。

## 置き場

`$OBSIDIAN_VAULT_DIR` が設定されていれば、project / topic を [`/kb`](../kb/SKILL.md) の「共通: 保存先の解決」と同じ手順で決め、
`$OBSIDIAN_VAULT_DIR/<project>/<topic>/<文書名>/` に `outline-YYYYMMDD.md` と `draft-YYYYMMDD.md`（必要なら `facts-YYYYMMDD.md`）を並べる。
未設定なら作業中のリポジトリに 1 文書 1 フォルダを切って同じ名前で置く。同日に 2 回目なら `-v2` を付ける。
公開先の言語で最初から書く（後で翻訳しない）。

Design Doc の確定版は topic 直下に `Design Doc.md`（既にあれば `Design Doc vN.md`、N = 既存の最大版 + 1）として置く。
旧版は変更しない。v2 以降は末尾に「vN-1 からの変更点」表を置く。

## 各段階の手順

### 0. 目的を 1 文で書く

「誰が、読み終わったあとに何を決められる／できるようになるか」を 1 文で、outline ファイルの冒頭に書く。
あわせて outline ファイルの末尾に、ゲートのチェックリスト（段階 0・1・2・4・5 ごとに `- [ ] 承認の言葉を受けた`）を写す。承認の言葉を受けたら印を付けてから次の段階へ進む。
依頼を受けた時点で「誰が何を決めるための文書か」をユーザーに聞き、答えをこの 1 文にする。依頼文から読めるときも、読めた 1 文を見せて確かめる。

分量は**字数の予算**で宣言する。まとめ（TL;DR）と本文を分け、本文は表を含めた字数にする。ページ数は媒体で長さが変わるので予算に使わない。
承認済みの予算を増やすときは、理由を添えてユーザーに確認する。**字数の指定が無ければ、本文 1,000 字以内を既定として提案する**。

**頼まれた文書だけを作る**。関連しそうな issue list・図・別ページの下書きを先回りで作らない。
会議の事前アジェンダは、会議で何が決まったかの出典にしない。事実として引くのは議事録で、アジェンダは仮の材料として扱う。

**文書の型も 1 つ宣言する**: 手順（やり方）／解説（仕組み・なぜ）／リファレンス（引く情報）／入門（最初の一歩）。
1 ページ 1 型にし、別の型の内容はリンクで外に出す（Diátaxis の分類）。**全面的な書き直し**のときは、既存ページの見出し・リンク・
残す事実をこの節の下に書き出してから進む（白紙から書き直さない）。

Design Doc のときは、topic フォルダの調査ノートと `ADR-*.md` を先に読む。ADR で決まっている事項は「決めること」に入れず前提として扱う。

### 0.5 ファクトシート（数字を含むレポートのとき）

実験結果・分析レポートのように数字が主張を支える文書では、H1 の前に `facts-YYYYMMDD.md` を同じフォルダに作る。
マニュアル・FAQ のように数字が主張を支えない文書では作らない。
収集はサブエージェントに任せ、数字ごとに次を 1 行ずつ書かせる: 値、モデル、実行回数と集計方法（例: 5 回の平均）、分母、
指標の定義（完全一致・許容一致など）、比較の起点、出所、確度タグ `[primary]`（原典で確認）/ `[summary-only]`（要約だけ）/ `[missing]`。
値より条件（分母・回数・起点）の誤りのほうが多いので、分からない欄は「要確認」、当てはまらない欄は「該当なし」と理由を書く。
メインは主張を支える数字を原典で確かめ直す。`[missing]` の主張と、手元の資料の外にありうる事実（チャットでの検証、
本番の挙動）は、「未実測」「未検証」と書く前にユーザーに聞く。

### 1. H1 アウトライン → rubric → ユーザー承認

先に house style があれば読む。用語と構成の型は H1 の段階で効く。
提案文書や Design Doc はそれぞれのテンプレートの構成に従う。Design Doc は [design-doc-template.md](./references/design-doc-template.md) に従い、
H1 の段階で Before/After、2 案以上の比較とトレードオフ、未確定事項を並べる節の 3 つがあるかを確かめる。
該当しない章は削除せず「なし」と理由を 1 行で書く。
検討して採らなかった案は、スコープ外ではなく案の比較の節に理由と一緒に書く。スコープ外には、今回扱わないと決めた課題だけを書く。

見出しになる 3〜6 項目を箇条書きで出し（調査計画・分析レポートなら「見る項目」を 1 項目 1 文で）、**承認を求める前に** 次の rubric 表を outline ファイルに書く。

| 観点 | 問い | 判定 |
|---|---|---|
| 目的との整合 | 各 H1 は 0 の目的に寄与するか。寄与しない項目は削れるか | ⭕️ / ❌ |
| 行動につながるか | 0 で決めた読者の行動に、どの H1 が答えるか（「理解する」が目的なら、何を理解するかが H1 に出ているか） | 同上 |
| 分量 | H1 1 項目 = 1〜3 段落として、宣言した分量に収まるか。収まらない項目はどこへ出すか | 同上 |

判定は ⭕️ / ❌ の 2 値にし、❌ には直す箇所を 1 行添える。どちらか迷う項目は問いが大きすぎる合図なので、2 つの問いに割る。

rubric 表の下に**用語表**を書く。読み手の語彙に無い語（実験の呼称・略語・チーム内の造語・分析の用語）を列挙し、
1 語ごとに平易な言い換え候補を 3〜4 個添えてユーザーに選んでもらう。採用した語はその文書の中で固定する。
ファイルのパスを示してから承認を求める。修正はファイルに反映してから次へ。承認前に H2 を書かない。

### 2. H2 展開 → rubric → ユーザー承認

H1 ごとに 2〜3 項目の H2 を足す。H3 は必要なときだけ。この段階で **制約・前提の出所** を確かめる。
H2 のうち事実・制約・数値を述べる項目には、出所（コード `path:line`、ユーザーの発言、調査ノートの `[[wikilink]]`、ADR など）を 1 語添える。
出所がチャットの過去発言だけの制約はユーザーに確認する（古い判断が新しい制約と矛盾していることがある）。
根拠のない数値は入れず「要確認」と書いてユーザーに決めてもらう。
定性的な主張（「〜が効く」「質が上がる」）には、出所つきの具体例を 1 つ添える。
rubric 表に 2 行足す: **重複**（同じ事実・考えが 2 つの H2 に出ないか）と **出所**（出所なしの制約が残っていないか）。
rubric 表を書いたら、承認を求める前に**外部レビュー**（下の「外部レビューの回し方」）を回し、事実の誤りは反映してから見せる。

### 外部レビューの回し方（段階 2 と 4 で共通）

別々のモデル 2 つに同じ依頼文を渡す。Codex CLI（`codex`）が使えればそれと Claude のサブエージェント、
使えなければモデルを変えた Claude のサブエージェント 2 つ（例: `opus` と `sonnet`）にし、代替したことをユーザーへの報告に書く。
2 つの指摘は一部しか重ならないので、2 モデルの結果がそろってから指摘を整理する。
2 モデルには同じ資料を渡す: 対象ファイル、段階 1・2 の rubric 表、採用済みの用語表、字数の予算、ファクトシート（作ったとき）、
照合する公開済みページ・関連する ADR。依頼文には次を書く。

- 目的の 1 文と読み手
- ユーザーが決めたことと採用済みの文言（レビューの前提として明記する）。これを書かないと、ユーザーの文言を戻す指摘が混ざる
- 見る観点: 目的に合うか、読み手が知らない用語・不自然な言い回し、公開済みの既存ページとの矛盾、字数の予算との差
- 出力の形: 重要な順に 12〜15 件まで、「重大度・場所・問題・修正案」

事実の誤り・矛盾・次の行動が不明な箇所は反映する。用語・言い回し・分量の指摘は、用語表と rubric に合うものを反映し、
迷うものはユーザーに回す。ユーザーが決めた文言とぶつかる指摘は、直さずにユーザーに戻す。

### 3. 段落化

H2 の 1 項目 = 1〜2 文を基本に、同じフォルダの `draft-YYYYMMDD.md` へ起こし、パスを示して見せる。
書き終えたら [prose-rubric.md](./references/prose-rubric.md) と house style を当て、**TL;DR の各行に本文の節があるか、本文の結論が TL;DR に出ているか** を確認する。
見せるときは、まとめと本文を分けて字数（日本語なら `LC_ALL=ja_JP.UTF-8 wc -m`、本文は表を含む）を測り、それぞれ「実測／承認済みの予算」を
1 行で並べる。超えていれば段落を削ってから見せる。

**本文の予算が 2,000 字を超える文書は、1 ターンに 1 段落ずつ起こす**。一度に全文を見せると、ユーザーが長い文章を一気に読むことになり、
後半ほど見落としが増える（コードレビューで 1 回 200〜400 行までとされるのと同じ理由）。1 ターンでは、H2 の順に次の 1 段落を draft に足し、
その段落と対応する H2 の項目だけをチャットに出す。ユーザーの返事（OK か直し）を受けてから次の段落へ進み、直しは後ろの段落の書き方にも反映する。
TL;DR・文体ルール・字数の確認は、全段落がそろってから上の手順どおり 1 回行う。ユーザーが「残りはまとめて」と言ったら、残りを 1 ターンで起こす。

### 4. 外部レビュー

「外部レビューの回し方」の 2 モデルに draft を渡す。観点に「節間の矛盾」「次に何をするか分からない箇所」「機械翻訳調」
「まとめの各項目が本文で支えられているか」と、字数の予算を超えた分の削り方を足す。
TL;DR と本文の重なりの指摘や数値の閾値要求はユーザーの判断に回す。反映後の draft をユーザーに見せる。
早く読み手に当てたいとユーザーが言ったときは、段階 3 の後に公開し、段階 4 を公開後の改訂として回してよい。

### 5. 公開

文体ルール・リンクの解決（wikilink は同じ project 配下の `**/<ノート名>.md` を Glob して確かめる）を確かめてから、ユーザーの最終承認を受けて公開する。
既定の公開は確定版ファイルの保存（Design Doc なら topic 直下の `Design Doc vN.md`、それ以外は `<文書名>/<文書名>.md`）。
外部のページ（Notion・Confluence・Claude Docs など）へは、ユーザーが公開先を指示したときだけ出す。
公開後にユーザーが公開先で手直ししたら、ページを再取得して **手元の draft を公開版に逆同期** する。
再発する修正は [prose-rubric.md](./references/prose-rubric.md) へ、工程の修正はこのファイルへ足す。

## よくある失敗

| 失敗 | 実際に起きること | 直し方 |
|---|---|---|
| rubric 表を書く前に承認を求める | ユーザーが骨格の穴を自分で探すことになる | 表を書いてから見せる（段階 1・2 の順序） |
| チャットの過去発言を制約として採用する | 古い判断が新しい制約と矛盾する | H2 の出所チェックでユーザーに確認する |
| 段落で「なぜ」を足す | 参照先ページと重複し、公開後にユーザーが削る | H2 に無い文を段落で増やさない。なぜはリンクで示す |
| 書き直しを新規作成として進める | 既存ページの有効な事実・リンクが落ちる | 段階 0 で既存内容の棚卸しをしてから書く |
| 逆同期を忘れる | 手元の draft が公開版と食い違い、次回の改訂が古い版から始まる | 公開後の手直しごとに再取得して同期する |
| 会議をまたいで使うディスカッションページを上書きする | 前回までの議論の経緯が消える | 既定は冒頭への追記（新しい回を上に足す）。上書きはユーザーが指示したときだけ |
| OKR・ADR などで既に決まっている事項を「決めること」に入れる | 決定済みの話を蒸し返し、本当に決めたい論点が埋もれる | 段階 0・1 で既存の合意を確かめ、決まっている事項は前提の節に書く |
| 個別の論点への回答を承認とみなして次の段階へ進む | 書いた本文が捨てになる | ゲートでは「〜はこれで承認ですか」と明示的に聞き、承認の言葉を待つ |
| 本文で表の中身を言い直す | 公開前にユーザーが段落ごと削る | 表を補う段落には、表に無い条件・具体例・読み手の判断への意味を書く |
| 対象を引用していない修正指示を推測で直す | 違う箇所を直す | 直す前に対象の文を引用して確認する |
