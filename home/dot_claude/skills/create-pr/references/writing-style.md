# PR本文の文体ガイド

ユーザー本人がレビュー依頼したPR（databricks / ivry-infra / datahub）の本文とレビュー返信から抽出したクセ。PRのタイトル・本文を書く・更新するときはこれに寄せる。

目指すのは「レビュアーに向けて本人が手で書いた文章」。網羅的な技術ドキュメントではない。

## 基本姿勢

- **短く書く。** 変更内容はdiffを見ればわかるので、本文は「なぜやるか」「どこを見てほしいか」「何をやっていないか」に使う
- **動機は一人称の素直な言葉で書く。** 気づいた・困った・やりたい、をそのまま書く
- **自明なことは書かない。** 1行で済む How は1行で終える。書くことが無いセクションは「ADRを参照」「#1234 の続編」のように一言で済ませてよい
- **盛らない。** 「体験を向上させる」「構造的に保証」「堅牢化」「〜を実現」のような宣伝調・抽象的な効能は書かない

## 文末と語調

- 箇条書きは常体・体言止めが基本（「〜を追加」「〜にした」「〜が必要」）
- What / Why の書き出しの1文は「〜します」「〜しました」の敬体も使う。1つのPR内で常体と敬体が混ざってよい
- 意図は「〜したい」「〜していきたい」で書く
  - 例: 「クエリを直書きで重いのでmart化していきたい」「公式のpracticeも変化してきたので追従したい」
- 迷い・相談は素直に書く
  - 例: 「PRを多く作るとレビューが大変だと思ったので一緒にしましたが、分けたほうが良ければ分けようと思います」
- くだけた言葉を無理に消さない: いい感じに / コケる / がっちゃんこする / しんどそう / ok / 一旦 / 雑に

## Why の書き方

きっかけ → 困りごと → だからやる、を2〜3文か箇条書きで。

```markdown
## Why

ダッシュボードに反映しようとしたら、workspace_nameも必要だったことに気づいたので追加します
```

```markdown
## Why

- ondemandのchatで日付指定されたときに、DateExtractorAgentがskipするようになっている
  - これはよい
- 一方で定期で実行すると前回実行のstateが残っているので、前の結果を参照してしまう
```

- ネストした箇条書きで「事実 → 補足・評価」を表す（上の「これはよい」のように短い合いの手も入れる）
- 発端がある場合はリンクを置く。ラベルは短く「発端」「スレ」「↓経由で相談してもらった。」程度
- 前後のPRとの関係を一言で書く: 「#2708 の続編」「#2280 の残作業」「#480 の続き。frontend側を実装した」
- 数字で根拠を示せるときは添える: 「`.py` 245 件あるのに規約が無く、237 件が要整形の状態」「pre-commitでの実行時間は0.3秒」

## What / How の書き方

- What はファイルごとの変更一覧にしない。何を足して何ができるようになるかを1〜2文の地の文で書く
  - 例: 「`profiles.yml` に新しいターゲットを追加し、既定でこれを使うようにした。〜に従って実行すると本番と隔離した環境で開発できるようになる」
- 変更点は箇条書き。ファイルパス・リソース名はバッククォートで囲む
- 補足はネストした箇条書きで短く足す（「↑ の2つをがっちゃんこするmodel」「diffが出ないようにこちらにも追記しています」）
- 参考にした既存実装・PRがあれば書く: 「#1977 の prod 実装パターンを踏襲して作成した」「pro/datahub を参考にし、stg との差分を発生させています」
- How の設計判断は、レビュアーが引っかかりそうな点だけ理由を添える。全判断を列挙しない
- 数値の置き換えや差分は `A` → `B` の矢印で書く

## やっていないこと・残作業

隠さずに書く。理由も素直に。

```markdown
## スコープ外

他のエッジケースは対応できていないが、そこまでやるのはしんどそうなのでskipした。例えば
```

- 「PRが膨れそうなのでスコープ外とした」「このファイルを触る PR で対処する」「次のPRで対応予定」
- テンプレートに該当セクションが無い場合、「スコープ外」「スコープ」「積み残し」「制限事項」の見出しを足してよい

## 手順・確認事項（インフラ系で特に）

- apply 順序や apply 後の手動作業はチェックリストか番号付きリストで明示する
- Check Points は「レビュアーが plan で確認すべきこと」を具体的に書く（「`databricks_grant` の新規追加が 2 件のみであること」）
- Check Points にはレビュアーが判断すべきことだけを書く。作成者が確認済みの動作確認は Remarks に一言で書き、コマンド列は書き下さない
  - 例: 「新規作成したコマンドが想定通りに動くこと」

## 表記のクセ

- ツール・サービス名は小文字でそのまま書くことが多い: claude / figma / mlflow / databricks / github actions
- 英単語と日本語の間にスペースを入れないことが多い（「sqlfluffを導入して」「pre-commitでsqlfmtを強制する」）。バッククォートで囲んだコードの前後はどちらでもよい
- 人名は `-san` を付ける（例: `xxx-san`）
- 例示は `e.g.`、簡易な対応は `->` / `↓` / `↑` を使う

## タイトル

- リポジトリの慣例のプレフィックスに従う（`feat(terraform):` / `fix:` / `stg/datahub:` / `vail:` など。慣例が無ければ付けない）
- 本文は日本語の体言止めを基本にする: 「〜を追加」「〜を修正」「〜作成」
- 分割したPRは「- その1」「- その2」を付ける

## 避けるもの（生成物っぽく見える書き方）

- 太字の見出し付き段落で設計判断を長々と並べる
- 「本 PR は〜」で始まる硬い文の連続
- テスト件数・カバレッジ・lint結果の列挙（CIで見えるので、特筆すべき検証だけ書く）
- コミットを1件ずつ説明する番号付きリスト（コミット構成がレビューに効くときだけ）
- 括弧（全角・半角とも）で詳細を補足する。ID・カタログ名・管理状態・前例などは、本文で要るなら地の文に入れ、要らなければ書かない
  - 例: 「SQL-XSS（`3cc5...`）を向けていた」→「SQL-XSSを向けていた」
- 「グレースフルデグラデーション」「堅牢化」「一貫性を確保」などの抽象語

## 本文例

```markdown
## What

コストダッシュボードに使うmartにworkspace_nameを追加します。そのために `system.access.workspaces_latest` を参照するモデルも追加します。

## Why

ダッシュボードに反映しようとしたら、workspace_nameも必要だったことに気づいたので追加します

## How

- `system.access.workspaces_latest` を参照するソースモデルを追加
- martに `workspace_name` カラムを追加（値が無い場合は `'none'`）

## Remarks

- apply は accounts -> workspaces の順に行う必要がある
```

## 注意

このファイルは公開リポジトリで管理している。例文を追加するときは顧客名・社内URL・Slackリンク・個人名を含めない。
